# 한 사람당 계정 하나: 기기 · 전화번호 · 로그인 수단 연결 (2026-11-16)

상태: **기획 초안. 사용자 확인 전이고, 구현된 것은 없다.**
표시: ✅ 사용자가 정함 · ❓ 아직 안 정함 · 🔎 코드에서 확인함 · ⚠️ 확인 못 함

## 1. 목표 ✅

한 사람당 계정 하나를 최대한 보장한다. 같은 기기, 같은 전화번호, 같은 로그인 수단으로 이어지는 것은 모두 같은 사람으로 본다. 한 계정을 영구 퇴출하면 이어진 계정·기기·번호가 함께 막히고, 그 기기나 번호로는 새로 가입할 수 없다. '영구 퇴출'을 신뢰 요소로 내세우기 위한 바탕이다.

## 2. 지금 코드에 있는 것 🔎

| 있는 것 | 내용 | 기기 식별로 쓸 수 있나 |
|---|---|---|
| `getOrCreateTrackingUserId` (`LivePhoneDemo/realtime-storage.ts`) | 웹 localStorage에 만든 임의 ID | 아니오. 앱을 지우면 사라진다 |
| `UserPushToken.installationId` | iOS는 UserDefaults, 안드로이드는 SharedPreferences에 만든 UUID. `(installationId, platform)`이 유일 | 부분적. 다시 깔면 바뀐다. 푸시를 허용해야 서버에 온다 |
| `AppEventLog.sessionKey` | 대화방 키 | 아니오 |
| 셸 → 웹 `capabilities` 메시지 (`rn/src/nativeCapabilities.ts`) | 기능 플래그만 보낸다. 기기 값은 없다 | 아니오 |
| `User.phoneE164`, `phoneHash`, `phoneVerifiedAt` | 인증된 번호. 번호는 유일하고, 다른 계정에서 인증하면 **옮겨 간다** | 번호 연결에 쓴다 |
| `User.moderationRestrictedAt` ('이용 제한', 운영툴 신고 화면) | 글·댓글·좋아요 쓰기만 403으로 막는다. 로그인, DM, 방 입장은 그대로다 | 퇴출 아님 |
| `signIn` 콜백 (`lib/auth-options.ts`) | `isDeleted` 계정의 로그인을 거부한다 | 퇴출 막기에 같은 자리를 쓴다 |

정리: **다시 깔아도 남는 기기 값은 지금 없다. 영구 퇴출도 지금 없다.** RN 셸에 키체인·기기 정보 라이브러리도 없다(`rn/package.json`).

## 3. 기기 식별값

| 플랫폼 | 값 | 다시 깔면 | 비고 |
|---|---|---|---|
| iOS | 키체인에 저장한 UUID (기본안) | 남는다 | 기기 초기화나 새 기기로 복원하면 바뀔 수 있다. `ThisDeviceOnly`로 저장해 다른 기기로 옮겨 가지 않게 한다 |
| iOS | Apple DeviceCheck 2비트 (선택) | 남는다 (초기화해도) | '퇴출됨' 표시용. 서버가 애플 API를 부른다. ❓ 1차에 넣을지 |
| 안드로이드 | `ANDROID_ID` (기본안) | 남는다 | 앱 서명 키 + 기기 사용자마다 고정. 공장 초기화하면 바뀐다 |
| 웹(브라우저) | localStorage ID | 지우면 사라진다 | 보조로만 기록한다 |

- 쓰지 않는 것 ✅: 광고 식별자(IDFA/GAID), 여러 특성을 조합한 핑거프린팅(애플 금지).
- 전달 방법: 셸이 페이지 로드 때 웹에 `deviceId`를 넘기고(지금 `capabilities` 메시지와 같은 길), 웹이 로그인·인증 요청에 `x-mingle-device-id` 헤더로 붙인다. 서버는 해시해서 저장한다.
- **네이티브 변경이라 앱 출시가 필요하다.** iOS 2.4.1이 11-15에 심사에 들어갔으므로 그다음 버전(2.4.2 또는 2.5.0)에 실린다. 그 전 버전과 웹은 localStorage ID와 `installationId`로만 기록한다(약한 연결).
- 서버만으로 지금 할 수 있는 것: 테이블, 전화번호·로그인 수단 연결, 필수 전화 인증, 퇴출과 가입 차단(번호·로그인 수단 기준). 기기 기준 차단만 앱 출시를 기다린다.

## 4. 데이터 구조 (사용자가 말한 모양 ✅)

```
AppDevice            기기 한 대
  id, platform(ios|android|web), deviceKeyHash(유일), keyKind(keychain|android_id|web_local|push_installation)
  firstSeenAt, lastSeenAt, blockedAt, blockedReason

AppDeviceUser        기기 ⇄ 유저 (다대다)
  deviceId, userId, firstSeenAt, lastSeenAt        @@unique(deviceId, userId)

AppDevicePhone       기기 ⇄ 전화번호
  deviceId, phoneHash, verifiedAt                  @@unique(deviceId, phoneHash)

AppUserPhone         유저에 딸린 번호 (한 번호는 한 계정에만)
  userId, phoneHash(유일), kind(primary|attached), verifiedAt, attachedViaDeviceId?

AppIdentityLink      연결이 생길 때마다 한 줄 (지우지 않는 기록, 운영툴용)
  userId, deviceId?, method(apple|google|email|phone), methodKeyHash, event(sign_up|sign_in|phone_verified|attached|detached), ip?, appVersion?, createdAt

AppIdentityBlock     막힌 것
  kind(device|phone|provider_account|email), keyHash, sourceUserId, reason, createdAt   @@unique(kind, keyHash)
```

- '같은 사람 묶음'은 따로 저장하지 않고, 위 연결을 따라가며 계산한다(유저 → 기기 → 다른 유저, 유저 → 번호 → 기기 → …). 가입자가 적으니 지금은 매번 계산해도 충분하다.
- 로그인 수단의 키: Apple·Google은 `Account.providerAccountId`, 이메일은 소문자 이메일, 전화는 `phoneHash`.
- 전화번호 원문은 지금처럼 `User.phoneE164`에만 둔다. 새 테이블에는 해시만 둔다. 단, 퇴출된 계정을 삭제해도 차단이 남아야 하므로 `AppIdentityBlock`은 유저 삭제와 함께 지우지 않는다.
- 🔎 지금 규칙 '다른 계정에서 번호를 인증하면 번호가 옮겨 간다'(`User.phoneE164` 주석)는 없앤다. 번호는 옮겨 가지 않고, 인증한 사람이 그 번호의 계정으로 들어간다(5절).
- 운영 DB: Prisma 마이그레이션으로 만들고, 사용자에게 알린 뒤 `psql -1 -v ON_ERROR_STOP=1`로 직접 적용한다. 새 테이블 추가뿐이라 지금 앱에 영향이 없다.

## 5. 같은 사람이 다른 수단으로 들어올 때 ✅

예: 애플로 가입한 사람이 같은 기기에서 구글로 '새로' 로그인하거나, 같은 번호를 인증한다.

| 안 | 동작 | 장점 | 단점 |
|---|---|---|---|
| 1. 자동 연결 | 새 계정을 만들지 않고 기존 계정으로 로그인시킨다 | 계정이 정말 하나로 유지된다. 사용자가 할 일이 없다 | **기기만 같다는 이유로 연결하면 다른 사람(가족, 중고폰)이 남의 계정에 들어간다.** 계정 탈취 위험 |
| 2. 안내 | "이 기기(번호)로 가입한 계정이 있어요. Apple로 로그인하세요"를 보여 주고 새 계정은 만들지 않는다 | 탈취 위험이 없다. 계정이 하나로 유지된다 | 예전 수단을 잃어버린 사람은 막힌다(문의 필요). 가족 공용 기기에서 두 번째 사람이 가입 못 한다 |
| 3. 묶음만 기록 | 새 계정을 만들고 같은 사람 묶음으로만 기록한다 | 누구도 막히지 않는다. 구현이 가장 작다 | 계정이 여러 개 생긴다. '한 사람 한 계정'은 퇴출 때만 지켜진다 |

**2026-11-16 사용자 결정 ✅: 기기만 같아도 같은 사람으로 본다.**

- **전화번호가 같다** → 안 1. 그 번호의 기존 계정으로 로그인시키고, 방금 쓴 로그인 수단을 그 계정에 붙인다. 방금 만들어진 빈 계정은 지운다. 본인이 문자 코드를 받았으므로 안전하다.
- **기기만 같다** → ✅ (2026-11-16 사용자 결정) 번호를 중심으로 기기·로그인 수단·번호를 모두 한 계정에 물들인다. 계정은 최소한으로만 만들어지게 한다.
  - 필수 전화 인증이 먼저이므로 실제 순서는 '새 수단으로 로그인 → 번호 인증 → 판정'이다.
  - 아래에서 A는 그 기기의 기존 계정이다. 기기에 계정이 여럿이면 그 기기에 가장 먼저 들어온(탈퇴·퇴출이 아닌) 계정을 A로 본다.
  - A에 인증된 번호가 없으면(예전 가입자): A로 자동 로그인하고 방금 인증한 번호를 A의 번호로 저장한다.
  - 방금 인증한 번호가 A의 번호와 같으면: A로 자동 로그인 (위 '전화번호가 같다'와 같은 경우).
  - **(1-1) 처음 보는 로그인 수단 + 처음 보는 번호 Y** (A의 번호는 X): "이 기기에서 쓰던 계정으로 들어갑니다"를 안내하고 A로 자동 로그인한다. 그 로그인 수단과 번호 Y는 A에 **딸린 것**으로 저장한다. 방금 만들어진 빈 계정은 지운다. 이후 Y나 그 로그인 수단으로는 어느 기기에서든 독립 계정을 만들 수 없고, 쓰면 A로 들어간다.
  - **(1-2) 이미 번호 Y로 인증을 마친 기존 계정 B로 그 기기에서 로그인**: 자동 로그인하지 않는다(B로 그대로 들어간다). "이 기기에 다른 계정이 있어요" 안내만 보여 준다. DB에는 A와 B를 같은 묶음으로 연결한다(같은 기기에 둘 다 기록). 두 계정은 따로 쓸 수 있지만 퇴출은 함께 간다.
  - 로그인 수단이나 번호가 새로 붙으면 A에 알림을 보낸다("새 로그인 수단이 연결됐어요").
  - (1-1)의 결과 ✅ (사용자 확인): 친구 폰을 빌려 자기 구글과 자기 번호로 들어온 사람은 친구 계정 A에 가입한 것이다. 그 번호와 수단은 A의 것이고, 폰 단속은 폰 주인의 몫이다.
  - **떼기 ✅**: A의 주인은 설정의 '로그인 수단' 목록에서 딸린 로그인 수단과 딸린 번호를 언제든 뗄 수 있다. 처음 가입 때 쓴 수단과 대표 번호는 뗄 수 없다(로그인 수단이 하나도 안 남는 일을 막는다).
    - 뗀 수단·번호로는 더 이상 A에 들어갈 수 없다. 그 수단으로 열려 있던 세션도 끊는다.
    - 뗀 뒤에는 특별한 규칙 없이 위 규칙이 그대로 적용된다. 같은 기기에서 다시 쓰면 (1-1)로 다시 A에 붙고, 다른 기기에서 쓰면 새 계정이 된다.
    - 뗀 기록은 지우지 않는다(`AppIdentityLink`에 `detached` 한 줄). 퇴출 묶음 계산에는 계속 들어간다.
    - 운영툴에서도 같은 떼기를 할 수 있다.
- **퇴출된 묶음에 닿는다** → 가입·로그인 거부.

'너무 폭력적인가'에 대해: 실제로 막히는 경우는 생각보다 적다.
- 중고폰: 공장 초기화를 하면 iOS 키체인 UUID와 `ANDROID_ID`가 모두 바뀐다. 초기화한 폰은 새 기기다.
- 탈퇴한 계정의 기기: 다시 가입할 수 있게 한다(퇴출자가 아니면).
- 남는 경우는 한 폰을 초기화 없이 둘이 쓰는 가족·친구뿐이고, 문의로 운영툴에서 푼다.
- 예외 목록이 꼭 필요하다: 운영진 테스트 폰, 심사 계정. 없으면 QA 폰 한 대에 계정 하나만 쓸 수 있다.
- 이 규칙은 네이티브 기기 값이 실린 앱 버전부터 제대로 동작한다. 그 전에는 번호 기준만 확실하다.

다른 사람이 같은 기기를 쓰는 경우 ✅:

- 가족·친구 공용: 둘 다 이미 계정이 있으면 (1-2)로 각자 쓴다. 두 번째 사람이 처음 가입하는 것이면 (1-1)로 A에 들어가고 독립 계정을 만들 수 없다. 문의가 오면 운영툴에서 뗀다.
- 중고폰: 공장 초기화를 했으면 새 기기다. 초기화하지 않았으면 (1-1)을 따른다.
- 한 기기에 연결된 계정 수: 새로 만들어지는 계정은 기기당 1개다. 이미 따로 있던 계정이 같은 기기로 들어오는 경우(1-2)만 여럿이 된다.

## 6. 필수 전화 인증 (기본안 ✅)

- 로그인 뒤 한 번 꼭 거친다. 애플·구글·이메일로 로그인해도 거친다. 전화번호로 로그인한 사람은 이미 끝난 것이다.
- 통과: `PHONE_REVIEW_LOGINS`의 심사용 번호, `REVIEW_ACCOUNT_EMAILS`의 심사 계정. 운영 계정(`OperatorAccount`)도 통과시킨다.
- 보내는 길은 #538 그대로: 한국 번호는 센드온 또는 솔라피, 해외는 Twilio.
- **구현됨 (2026-11-16, #543 브랜치)**: 환경변수 `PHONE_REQUIRED=on`. 화면은 `components/onboarding/phone-gate.tsx`, 판정은 `server/app-access.ts`의 `needs_phone`. 서버가 문자를 보낼 수 없으면(문자 키가 하나도 없으면) 켜 둬도 아무에게도 묻지 않으므로, 키보다 먼저 켜도 잠기지 않는다.
- ✅ 기존 계정도 모두 필수다 (사용자 결정). 다음에 앱을 열 때 한 번 인증한다.
- ⚠️ 지금은 대화목록 화면에서만 막는다(초대 게이트와 같은 자리). 피드·탐색·마이 탭은 막지 않는다. 홈 탭을 만들 때 모든 탭으로 넓힌다.
- ✅ 말해 보기를 건너뛴 기존 계정: 말해 보기는 시키지 않고 원래 하던 다음 단계로 간다.
- ❓ 문자가 안 오는 사람(Twilio 미지원 국가, 가상 번호): 문의 → 운영툴에서 수동 통과.
- ⚠️ 애플 심사: 애플로 로그인한 사람에게 전화번호를 꼭 받는 것은 가이드라인 4.8·5.1.1에서 지적받을 수 있다. '사기·악용 방지를 위한 본인 확인'으로 심사 메모에 설명하고, 인증 화면에도 이유를 한 줄 적는다. 반려되면 (나)처럼 '사람과 대화를 시작할 때 요구'로 물러난다.
- 문자 비용·남용 한도는 #538 그대로(번호당 하루 5번, IP당 하루 10번).

## 7. 퇴출

- 새 동작 '영구 퇴출'을 운영툴 신고 화면에 추가한다. 지금의 '이용 제한'(글쓰기만 막음)은 그대로 둔다.
- 퇴출하면:
  1. 그 계정에서 연결을 따라가 닿는 모든 계정·기기·번호·로그인 수단을 찾는다. **실행 전에 운영툴이 목록을 보여 주고 운영자가 확인한다** (공용 기기로 엉뚱한 사람이 딸려 오는 것을 막기 위해).
  2. 그 계정들에 `bannedAt`을 찍고 세션과 푸시 토큰을 지운다.
  3. 기기·번호·로그인 수단을 `AppIdentityBlock`에 넣는다.
- 막는 자리: `signIn` 콜백(지금 `isDeleted`를 거부하는 곳), 전화 코드 요청과 확인, 기기 헤더가 있는 가입 요청. 화면에는 "이용이 영구 제한된 계정입니다"와 문의 주소만 보여 준다.
- 풀기: 운영툴에서 계정 단위, 기기 단위로 따로 풀 수 있게 한다. 모두 `AdminAuditLog`에 남긴다.
- 홈의 "이번 주 영구 퇴출 N명" 공지(`docs/home-explore-rooms-plan.md` 2절)는 이 퇴출 기록에서 만든다.
- ❓ 계정 삭제(탈퇴) 뒤 재가입: 퇴출자가 아니면 허용하는 것으로 제안한다. 연결 기록은 재가입 뒤에도 같은 사람으로 이어지게 남긴다(8절 보관 기간 참고).

## 8. 개인정보와 스토어

- App Store 개인정보 라벨: '식별자 – 기기 ID' 추가 (목적: 앱 기능, 사기 방지. 추적에는 쓰지 않음).
- Play 데이터 보안: '기기 또는 기타 ID' 추가 (목적: 사기 방지·보안·규정 준수).
- 개인정보처리방침(`translator.minglelabs.app` 법률 페이지): 수집 항목에 기기 식별값과 전화번호, 목적(중복 가입과 퇴출 회피 방지), 보관 기간을 적는다.
- ❓ 보관 기간: 탈퇴한 일반 사용자의 기기·번호 해시는 얼마나 둘지(제안: 1년), 퇴출자의 차단 기록은 얼마나 둘지(제안: 기한 없음, 방침에 명시). 법률 검토는 하지 않았다 ⚠️.
- 모든 값은 해시(서버 비밀값을 섞은 HMAC)로만 저장한다.
